# @runa-cmd/core — Feedback & Roadmap Suggestions

> Analysis performed on v0.1.0 (April 2026). The goal of this document is to help the project mature — the foundations are solid.

## What's Working Well

- Clean architecture with clear module boundaries
- Full type inference from Zod schemas to `run()` handler
- Plugin system with capability-based access control and topological sort
- Middleware with onion model (Koa/Hono style)
- 4 real packages (core, help, mcp, completions) — all substantive, not stubs
- ~38 test files with ~9K lines of test code
- Zero runtime deps in core (as claimed)

---

## 🔴 Critical Issues (Blockers)

### 1. `process.exit(0)` in help plugin

`packages/help/src/plugin.ts:60` — Calling `process.exit()` in library code prevents async cleanup hooks from completing and breaks embedded usage/testing. The `shortCircuit()` call on line 59 should be sufficient.

**How to fix:** Remove the `process.exit(0)` call entirely. The `shortCircuit()` mechanism already stops the lifecycle. If needed, let the consumer decide when to exit by exposing an `exitOnHelp` option in the plugin config (default `false`).

**How others solve it:** Commander uses `outputHelp()` which just prints without exiting, and `help()` which calls `process.exit()` — but the choice is the consumer's. oclif uses an `exit()` method that can be overridden in tests.

### 2. Unknown flags silently ignored

`packages/core/src/parse/parseargs-bridge.ts:80` sets `strict: false`, expecting Zod to catch unknown options. But Zod only validates known keys — `--typo-flag` passes through silently with no error.

**How to fix:** After Zod validation, compare parsed keys against defined option keys. Any unknown key should throw a `ValidationError` with a "did you mean?" suggestion (you already have Levenshtein).

**How others solve it:** Commander throws `error: unknown option '--foo'` by default. yargs has `strict()` mode. Both are opt-out, not opt-in.

### 3. `--` separator not supported

Standard POSIX convention for "stop parsing options". Required for any CLI that may receive arguments starting with `-`.

**How to fix:** Node's `util.parseArgs` already supports `--` natively — tokens after it go to `positionals`. You just need to pass `allowPositionals: true` and not strip `--` before parsing. Forward everything after `--` as-is in `RunContext` (e.g., `ctx.rest: string[]`).

**How others solve it:** Commander exposes `.passThroughOptions()` and collects rest args. yargs uses `--` natively with `argv._`.

### 4. Coupled to Zod v4 internals (`._zod.def`)

The schema walker accesses private Zod structures. A minor Zod update changing internals breaks the entire parsing pipeline.

**How to fix:** Create a `SchemaAdapter` interface that extracts type info, defaults, and descriptions from a schema. Implement `ZodV4Adapter` using current logic. This isolates breakage to one file and makes supporting other schema libs (Valibot, ArkType) possible.

**How others solve it:** citty uses its own schema format (no Zod dependency). oclif uses its own flag definitions. The tradeoff is less ergonomic schemas vs. zero coupling risk.

### 5. Empty string coerces to `0` for numbers

`Number("")` returns `0` and `isNaN(0)` is `false`, so `--port ""` silently becomes `--port 0`.

**How to fix:** Check for empty/whitespace-only strings BEFORE calling `Number()`:

```typescript
if (typeof value === 'string' && value.trim() === '') {
  throw new ValidationError(`Option --${key} requires a numeric value`);
}
```

### 6. No CI/CD

No GitHub Actions, no automated tests on PR, no release pipeline. Any PR can silently break things with zero feedback.

**How to fix:** Start with a minimal GitHub Actions workflow: `test` + `build` on PR, `release` on main push. Use `pnpm -r run test` and `pnpm -r run build`. Add changesets for versioning.

**Reference:** A minimal monorepo CI setup:
- [changesets/action](https://github.com/changesets/action) for automated releases
- Matrix: `os: [ubuntu-latest, windows-latest]`, `node: [18, 20, 22]`

### 7. No Windows testing

Uses POSIX signals (SIGINT/SIGTERM) and shell scripts for completions. Behavior on Windows is unknown and likely broken.

**How to fix:** Add `windows-latest` to CI matrix. Wrap signal handlers with platform checks (`process.platform !== 'win32'`). For completions, PowerShell support can come later — but the core + help packages should work cross-platform from day one.

**How others solve it:** Commander and yargs both run CI on Windows. oclif has extensive Windows support docs.

## 🟡 Feature Gaps

| Gap | Detail | Suggested fix | Reference |
|-----|--------|---------------|-----------|
| **No `--version` built-in** | Requires manual setup | Add a `versionPlugin()` in `@runa-cmd/help` that intercepts `--version/-V`, reads `meta.version` | Commander: `.version()` is one line |
| **No repeated options** | `--tag a --tag b` not supported | Use `multiple: true` in `parseArgs` config when Zod type is `z.array()` — you already detect arrays in the schema walker | yargs: array options built-in |
| **No stdin/pipe support** | `echo "data" \| my-cli` doesn't work | Add `ctx.stdin` to `RunContext` that reads from `process.stdin` when not a TTY. Could be a middleware or core feature | Commander: no built-in, but trivial. citty: no built-in either |
| **`deploy --help` doesn't work** | Help intercepts at `onGlobalFlags` before command resolution | In the help plugin, defer rendering to `afterParse` when a positional arg exists alongside `--help`. Resolve the command first, then render its help | Commander: `--help` works anywhere in argv |
| **Global/command option collision** | Plugin global option steals tokens silently | In `defineCLI`, validate that no global option name overlaps with any command option. Throw at definition time, not runtime | oclif: warns on flag name conflicts |
| **CJK/emoji break table layout** | `visibleWidth` ignores wide characters | Use Unicode East Asian Width property. [string-width](https://github.com/sindresorhus/string-width) is the standard solution (or port its logic to stay zero-dep) | ink, blessed: all use string-width |
| **`#RGB` hex shorthand rejected** | Only `#RRGGBB` accepted | Expand regex to `/^#([0-9a-f]{3}|[0-9a-f]{6})$/i` and duplicate short digits (`#F0A` → `#FF00AA`) | CSS spec behavior |
| **`onError` swallows exceptions** | `cli.ts:427` catches errors from error handlers with zero logging | At minimum `console.error('onError handler threw:', err)`. Better: emit a `fatalError` event | Commander: error handler errors propagate |
| **Levenshtein threshold fixed at 3** | Suggests absurd matches for short inputs | Use `Math.ceil(input.length * 0.4)` or `Math.min(3, Math.floor(input.length / 2))` as threshold | git: uses proportional threshold |

## 🟠 Missing for Framework Completeness

Features that competing frameworks offer and users will eventually expect:

| Feature | Notes | Reference |
|---------|-------|-----------|
| **Interactive prompts** | Inquirer/Clack integration or built-in primitive | oclif: `@oclif/prompts`. citty: no built-in. Consider a `@runa-cmd/prompts` package |
| **Progress bars / spinners** | Common need for long-running commands | ora, listr2 — could be a `@runa-cmd/ui` package with your existing `box()`/`table()` primitives |
| **Default command** | Run without subcommand name | Commander: `.defaultCommand()`. Could use a `default: true` property in `CommandConfig` |
| **Tab completion for file paths** | Currently only enum values get completed | zsh/bash have `_files` and `compgen -f` — hook into shell builtins for path arguments |
| **YAML/TOML config loaders** | Only JSON built-in | Ship as `@runa-cmd/config-yaml`, `@runa-cmd/config-toml`. Or document cosmiconfig integration |
| **Changesets / release automation** | No versioning strategy configured | [@changesets/cli](https://github.com/changesets/action) — standard for monorepo releases |
| **Coverage reporting** | Not configured in vitest | `vitest --coverage` with thresholds in CI. Start with 80% and increase as you harden |

**Key differentiators to lean into:** Zod schema-driven, full type inference, MCP built-in, plugin + middleware architecture. These are genuine advantages no competitor has today.

**Key gap to close fast:** Production hardening (CI, Windows, strict parsing). Without this, technical users won't trust it for real projects regardless of how good the DX is.

## Suggested Prioritization

**Phase 1 — Correctness & Infrastructure**
1. Add CI/CD (GitHub Actions: test, lint, build on PR)
2. Fix `strict: false` — reject unknown flags
3. Support `--` separator
4. Remove `process.exit()` from help plugin
5. Fix empty string → number coercion
6. Add Windows CI matrix

**Phase 2 — Hardening**
7. Abstract Zod internals behind an adapter
8. Add coverage reporting + changesets
9. Fix `deploy --help` command resolution order
10. Add option name collision detection
11. Log errors in `onError` catch block

**Phase 3 — Feature Completeness**
12. Built-in `--version` flag
13. Repeated/array options (`multiple`)
14. Stdin support
15. CJK/emoji-aware `visibleWidth`
16. Default command support
17. Interactive prompts / spinners (or documented integration path)

---

*Overall: the architecture and code quality are well above average for an alpha project. The main gap is production hardening, not design. The Zod-driven DX and MCP integration are genuine differentiators — lean into them. With the fixes above, this could become a serious alternative in the CLI framework space.*
